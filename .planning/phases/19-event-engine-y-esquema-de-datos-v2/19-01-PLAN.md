class Severity(str, Enum):
    INFO = "info"
    WARNING = "warning"
    CRITICAL = "critical"


class Event(BaseModel):
    id: str                       # uuid4, generado por defecto
    type: EventType
    camera_id: str
    ts: datetime
    severity: Severity = Severity.INFO
    track_id: int | None = None
    person_id: int | None = None

    confidence: float | None = None

    snapshot_path: str | None = None
    recording_id: int | None = None
    payload: dict[str, Any] = Field(default_factory=dict)


class EventBus:
    def subscribe(self, name: str, handler: Callable[[Event], Awaitable[None]]) -> None: ...
    def unsubscribe(self, name: str) -> None: ...
    async def publish(self, event: Event) -> None: ...

    @property
    def stats(self) -> dict[str, int]: ...

    - test_stats_counts_published_and_failed: `stats` refleja publicados y fallos de handler.
    - test_queue_is_bounded: la cola interna tiene maxsize; al llenarse se descartan los eventos mas antiguos y se contabiliza en `stats["dropped"]`.

  <action>
Crear `backend/events/bus.py`.

Puntos criticos:

1. **`publish_threadsafe`** es el unico puente permitido hilo → asyncio. Usa `loop.call_soon_threadsafe`. Los workers de la Fase 18 son hilos, asi que este es el metodo que usaran.

2. **Cola acotada** (`maxsize`, default 1000). Un desbordamiento significa que el consumidor no da abasto; se descarta el evento mas antiguo y se cuenta. Nunca se bloquea al emisor.

3. **Aislamiento de handlers**: cada handler se ejecuta en su propio `asyncio.Task` con `try/except` — un handler que lanza no puede afectar a los demas ni al bus.

4. **Identidad del objeto**: no serializar entre suscriptores. El mismo `Event` se pasa por referencia. La serializacion ocurre en el borde (persistencia y WebSocket), no en el bus.

Escribir primero los 7 tests con `pytest-asyncio` (RED). Anadir `pytest-asyncio>=0.24` a `requirements.txt` y configurar `asyncio_mode = auto` en `pytest.ini` si no lo esta.

`run_migrations(engine)`:
1. Lee `app_config['schema_version']` (0 si no existe).

3. Copia `data/events.db` a `data/backups/events-{YYYYmmdd-HHMMSS}.db`.
4. Aplica las migraciones pendientes en orden dentro de una transaccion.
5. Escribe la nueva `schema_version`.

- Insertar una fila en `cameras` para `'cam1'`.
- Convertir `crossing_events` en filas de `events` con `type='LINE_CROSSED'`, `ts` del timestamp original y `payload={"direction": ...}`.
- **No borrar `crossing_events`.** Se deja como respaldo en caliente; se retirara en una fase posterior una vez validado.
